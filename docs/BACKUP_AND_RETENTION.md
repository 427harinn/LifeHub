# LifeHub バックアップ・データ保持仕様

## 1. 目的

LifeHubは個人用の長期利用アプリであり、予定・お金・日メモを長期間残す。
一方で、Cloudflare D1へ無期限に履歴を蓄積し続けて不要な容量増加・将来的な課金要因を作らないようにする。

そのため、LifeHubでは以下を分離する。

- 最近のデータ: Cloudflare D1
- 古い履歴: 端末IndexedDB
- 機種変更・復元用: JSONバックアップ

---

## 2. 基本方針

- ユーザーが過去データを失わずに使い続けられることを優先する
- 古いデータを単純削除しない
- D1から削除する前にローカルアーカイブ保存成功を必ず確認する
- ローカルアーカイブ後も通常のCalendar / Daily / Moneyから閲覧可能にする
- 機種変更時に、クラウド・ローカル双方を含む完全なJSONを書き出せるようにする
- 機種変更中はアカウントを通常利用できない状態へ切り替え、インポート完了後に再開する

---

## 3. 保存先

### 3.1 D1

最近の予定・お金・メモ・設定等を保持する。

D1は以下に向く。

- 現在〜近い過去のCalendar表示
- 通知計算に必要な予定
- recurrence定義
- 最近のMoney集計
- 最近の検索

### 3.2 IndexedDB

一定期間より古い履歴を端末内に保存する。

対象:

- 過去Event
- Event occurrence override
- 過去Money occurrence / override
- DailyNote
- 過去表示に必要な最低限の関連データ

localStorageではなく、構造化データ・件数増加に向くIndexedDBを利用する。

### 3.3 JSONバックアップ

機種変更・復元時に使う正本。
端末内アーカイブとD1の双方をまとめて1ファイルにする。

---

## 4. クラウド保持期間

初期仕様では **直近1年分をD1に保持**する。

重要:

- recurrenceの親定義など、未来の予定生成に必要なデータは「古い」という理由だけで削除しない
- 現在も続くMoneyItem定義もD1に残す
- 古い履歴だけをIndexedDBへ退避する

---

## 5. アーカイブ対象判定

単純に `createdAt` で判断しない。

### 単発Event

終了日時が保持境界より前で、今後参照すべきクラウド上の関連処理がない場合に候補。

### 終了済みrecurrence系列

recurrence endsOn が保持境界より前で、今後発生しない場合に候補。

### 現在も続くrecurrence

親Event / RecurrenceRuleはD1に残す。
古いoccurrence override等だけをアーカイブ対象にできる。

### Money

過去月のoccurrence / actual / estimated_actualはアーカイブ可能。
現在も続く定期MoneyItem定義はD1へ残す。

### DailyNote

対象日が保持境界より前なら候補。

---

## 6. 自動アーカイブの推奨タイミング

**各予定のちょうど1年後に個別処理する方式は採用しない。**
予定ごとのタイマー管理が複雑になるため。

また、12月31日に年1回まとめて処理すると、同じ年の1月データと12月データでクラウド保持期間が大きく変わる。

そのため初期推奨案は:

- 月1回、または月初のアプリ起動時
- `現在日から12か月より古い履歴` をまとめて候補化

とする。

例:

2027年10月1日時点では、2026年10月1日より前のアーカイブ可能履歴を対象にする。

ローカルIndexedDBへの保存が必要なので、サーバーCronだけで勝手に削除しない。

---

## 7. アーカイブ処理

安全性を優先し、以下の順序を必須とする。

1. D1からアーカイブ対象を取得
2. IndexedDBへ保存
3. 保存した件数・ID・checksum等を検証
4. ローカル保存成功状態を記録
5. その後にのみD1から対象履歴を削除
6. アーカイブメタデータを更新

途中失敗時はD1削除を実行しない。

「先にDBから削除して後で保存」は禁止する。

---

## 8. 過去データの読み込み

Calendar等が古い期間を表示するとき:

1. 対象期間がD1保持範囲内 → APIから取得
2. ローカルアーカイブ対象 → IndexedDBから取得
3. 境界月など両方にまたがる場合 → merge

UI側では保存先を意識させない。

---

## 9. JSONエクスポート内容

機種変更用JSONには、LifeHubのCalendar / Daily / Moneyを再構築できる情報をすべて含める。

最低限:

- schemaVersion
- exportedAt
- appVersion
- user settings
- Event
- RecurrenceRule
- EventOccurrenceOverride
- EventNotification
- NotificationTemplate / offsets
- DailyNote
- MoneyItem
- Money recurrence / occurrence override
- actual / estimated_actual
- MoneyCategory
- D1に残っている履歴
- IndexedDBへアーカイブ済みの履歴
- アーカイブメタデータ

秘密情報は含めない。

- session token
- password hash
- VAPID private key
- Cloudflare secret

---

## 10. 機種変更モード

通常のバックアップとは別に、設定画面に明確な `機種変更` 導線を持つ。

ユーザーの意図:

- 新しい端末へ完全移行する
- 旧クラウドデータを残したまま二重運用しない
- 移行開始後はインポート完了まで通常利用しない

### 推奨フロー

1. `機種変更を始める`
2. 強い確認画面を表示
3. D1 + IndexedDBから完全JSONを生成
4. JSON schema / 件数 / checksumをローカルで検証
5. ユーザーがファイルを保存
6. 保存したJSONを再選択して検証する、または明示的な最終確認を行う
7. `このバックアップで機種変更を開始` を実行
8. D1の移行対象データを削除
9. アカウントを `migration_locked` 状態へする
10. 新端末で同アカウントへログイン
11. JSONをインポート
12. 復元成功後に `migration_locked` を解除

### 重要

ブラウザは「ユーザーがファイルを確実に保存できた」ことを完全には保証できない。

そのため、単一のエクスポートボタンを押した瞬間に無条件でD1を削除するのではなく、**JSON生成・検証後に別の最終確認を置く**ことを推奨する。

機種変更は稀な操作なので、安全性を優先する。

---

## 11. migration_locked 中の挙動

アカウントが機種変更中の場合:

- Calendar / Daily / Moneyの通常操作は不可
- 新規Event / Money登録不可
- 編集 / 削除不可
- 通知スケジュール対象から除外可能
- 画面は機種変更専用UIへ誘導

可能な操作:

- バックアップJSONのインポート
- 必要なら機種変更キャンセル / 復旧導線（実装時に安全性を検討）

---

## 12. JSONインポート

新端末への復元専用として扱う。
初期仕様では既存データとの一般的なマージ用途には使わない。

前提:

- migration_locked状態
- 新端末側に通常データがない

処理:

1. schemaVersion確認
2. JSON全体validation
3. checksum確認
4. 件数・対象期間確認
5. 最近1年分と将来必要な定義をD1へ復元
6. 1年より古い履歴をIndexedDBへ復元
7. Calendar / Money再構築検証
8. 復元成功後にmigration lock解除

重複マージを初期仕様の中心にはしない。

---

## 13. CSV

CSVはバックアップの正本にしない。

理由:

- recurrence
- 複数通知
- occurrence override
- metadata

などの関係を完全に表現しにくいため。

閲覧・表計算用途として将来的に以下を出力してもよい。

- 予定一覧.csv
- お金一覧.csv

機種変更・復元はJSONを正とする。

---

## 14. 通常バックアップとの違い

将来的に `バックアップを書き出す` だけの機能を持つ場合、それはD1を削除せず、アカウントもロックしない。

- 通常バックアップ: コピーを作るだけ
- 機種変更: 完全JSON確認後にD1整理 + migration lock

ユーザーが誤操作しないようにUI上で明確に分ける。

---

## 15. 削除との違い

ユーザーが予定詳細から押す「削除」と、自動アーカイブは別物。

- 削除: ユーザーがその予定を不要として消す操作
- アーカイブ: 過去履歴を保持したまま保存先をD1から端末へ移す操作
- 機種変更: 完全バックアップを新端末へ移し、旧クラウド状態を整理する操作

アーカイブされた予定はCalendar上から消えない。
