# LifeHub バックアップ・データ保持仕様

## 1. 目的

LifeHubは個人用の長期利用アプリであり、予定・お金・日メモを長期間残す。
一方で、Cloudflare D1へ無期限に履歴を蓄積し続けて不要な容量増加・将来的な課金要因を作らないようにする。

そのため、LifeHubでは以下を分離する。

- 最近のデータ: Cloudflare D1
- 古い履歴: 端末IndexedDB
- 機種変更・復元用: JSONバックアップ

---

## 2. 基本方針

- ユーザーが過去データを失わずに使い続けられることを優先する
- 古いデータを単純削除しない
- D1から削除する前にローカルアーカイブ保存成功を必ず確認する
- ローカルアーカイブ後も通常のCalendar / Daily / Moneyから閲覧可能にする
- ローカルアーカイブは端末依存であることを明示する
- 機種変更前にJSONバックアップを書き出せるようにする
- JSONインポートで新端末へ復元できるようにする

---

## 3. 保存先

### 3.1 D1

最近の予定・お金・メモ・設定等を保持する。

D1は以下に向く。

- 現在〜近い過去のCalendar表示
- 通知計算に必要な予定
- recurrence定義
- 最近のMoney集計
- 最近の検索

### 3.2 IndexedDB

一定期間より古い履歴を端末内に保存する。

対象:

- 過去Event
- Event occurrence override
- 過去Money occurrence / override
- DailyNote
- 過去表示に必要な最低限の関連データ

localStorageではなく、構造化データ・件数増加に向くIndexedDBを利用する。

### 3.3 JSONバックアップ

端末ローカルだけでは、ブラウザデータ削除・端末故障・機種変更で失われる可能性がある。

そのためユーザーがファイルとして保存できるJSONエクスポートを正式機能にする。

---

## 4. クラウド保持期間

初期仕様では **直近2年分をD1に保持**する案を採用する。

理由:

- Calendarで現実的に頻繁に参照する範囲として十分広い
- Moneyの前年・前々年比較がしやすい
- 古い履歴を永続的にD1へ増やし続けない

保持期間は将来設定変更可能にしてもよいが、初期UIでは固定値で構わない。

重要: recurrenceの親定義など、未来の予定生成に必要なデータは「古い」という理由だけでアーカイブ・削除しない。

---

## 5. アーカイブ対象判定

単純に `createdAt` で判断しない。

予定の場合は、その予定・occurrenceが完全に過去となり、今後の発生に必要ないことを確認する。

### 単発Event

終了日時がクラウド保持期間より前なら候補。

### 終了済みrecurrence系列

recurrence endsOn が保持境界より前で、今後発生しない場合に候補。

### 現在も続くrecurrence

親Event / RecurrenceRuleはD1に残す。
古いoccurrence override等だけをアーカイブ対象にできる。

### Money

過去月のoccurrence / actual overrideはアーカイブ可能。
現在も続く定期MoneyItem定義はD1へ残す。

### DailyNote

対象日が保持境界より前なら候補。

---

## 6. アーカイブ処理

安全性を優先し、以下の順序を必須とする。

1. D1からアーカイブ対象を取得
2. IndexedDBへ保存
3. 保存した件数・ID・checksum等を検証
4. ローカル保存成功状態を記録
5. その後にのみD1から対象履歴を削除
6. アーカイブメタデータを更新

途中失敗時はD1削除を実行しない。

「先にDBから削除して後で保存」は禁止する。

---

## 7. 自動アーカイブ

初期版では、サーバーCronだけで勝手にD1データを消さない。

ローカルIndexedDBへの保存が必要なため、ユーザーの端末が関与する必要がある。

推奨フロー:

- アプリ起動時などに「アーカイブ可能データあり」を確認
- バックグラウンドで端末へ取得・保存
- 保存検証後、APIへアーカイブ完了を通知
- APIがD1履歴を削除

初期実装では完全自動化せず、設定画面から `古いデータを端末へ移動` を実行する方式でもよい。

安全性を優先して段階導入する。

---

## 8. 過去データの読み込み

Calendar等が古い期間を表示するとき:

1. 対象期間がD1保持範囲内 → APIから取得
2. ローカルアーカイブ対象 → IndexedDBから取得
3. 境界月など両方にまたがる場合 → merge

UI側では可能な限り保存先を意識させない。

同一IDの重複がある場合はD1側を優先するなど、merge ruleを実装時に固定する。

---

## 9. JSONエクスポート

設定画面に `バックアップを書き出す` を置く。

JSONには以下を含める。

- schemaVersion
- exportedAt
- appVersion
- user settings
- Event / recurrence
- Event override
- notification設定
- DailyNote
- MoneyItem / Money override / category
- D1に残っている履歴
- IndexedDBへアーカイブ済みの履歴

つまり「クラウド分だけ」「ローカル分だけ」ではなく、**ユーザーのLifeHubデータ全体を1つにまとめる**。

秘密情報は含めない。

- session token
- password hash
- VAPID private key
- Cloudflare secret

などはエクスポート対象外。

---

## 10. JSONインポート

新端末・復元時にバックアップJSONを読み込めるようにする。

インポート時:

1. schemaVersion確認
2. JSON全体のvalidation
3. 件数・期間をユーザーへ表示
4. 復元実行
5. 重複データをID等で判定

初期仕様では「既存データとマージ」を基本とし、全消去して置換は高度な操作として扱う。

古いアーカイブ対象データはIndexedDBへ、最近必要なデータは必要に応じてD1へ戻す。

---

## 11. CSV

CSVはバックアップの正本にしない。

理由:

- recurrence
- 複数通知
- occurrence override
- metadata

などの関係を完全に表現しにくいため。

ただし閲覧・表計算用途として将来的に以下のCSV出力は有用。

- 予定一覧.csv
- お金一覧.csv

機種変更・復元はJSONを正とする。

---

## 12. バックアップ通知

最終エクスポートから長期間経過し、かつローカルアーカイブが存在する場合は設定画面等で軽く注意を出してよい。

強制通知や頻繁な警告にはしない。

例:

`端末内にのみ保存されている過去データがあります。バックアップ: 6か月前`

---

## 13. 削除との違い

ユーザーが予定詳細から押す「削除」と、自動アーカイブは別物。

- 削除: ユーザーがその予定を不要として消す操作
- アーカイブ: 過去履歴を保持したまま保存先をD1から端末へ移す操作

アーカイブされた予定はCalendar上から消えない。
