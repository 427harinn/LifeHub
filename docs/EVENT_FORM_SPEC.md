# LifeHub Event登録フォーム仕様

## 1. 目的

LifeHub の家・仕事予定登録フォームについて、ユーザーが予定を考える自然な順番に沿って入力できるようにする。

HouseToDo のフォーム思想を継承し、**入力に必要のない項目は最初から提示しない**。

フォームは「全部の項目を並べる」のではなく、上から入力するにつれて、その選択に必要な次の項目だけが現れる Progressive Disclosure を基本とする。

---

## 2. 最重要設計原則

### 2.1 頭の中で考える順番とフォーム順を一致させる

予定を登録するときの自然な思考順は以下とする。

1. 何の予定か
2. 日時が決まっているのか、期間中にやりたいのか
3. いつなのか
4. それを繰り返すのか
5. 通知が必要か
6. 場所やメモを付けるか

フォームもこの順番に合わせる。

### 2.2 不要な入力欄は表示しない

例:

- 「日時が決まっている」を選ぶまで日時入力を出さない
- 「期間中にやりたい」を選んだ場合、時間入力を出さない
- 終日ONなら時間入力を隠す
- 繰り返しなしなら曜日・終了日等の詳細を出さない
- 通知なしなら通知詳細を出さない
- 場所・メモは未使用時はコンパクトな行だけにする

### 2.3 1画面の中で完結させる

HouseToDo の家事登録画面と同じく、基本的には1つの登録画面で完結させる。

詳細設定は BottomSheet を使う。

不要な中間ページやステップ形式ウィザードは作らない。

---

## 3. 基本フォーム順

家・仕事は同一フォームを使用し、カテゴリだけ入口で固定する。

基本順:

1. 以前の項目から選ぶ
2. タイトル
3. 予定の種類
4. 日時 / 実施時期
5. 繰り返し
6. 通知
7. 場所
8. メモ
9. 登録

「予定の種類」と「日時 / 実施時期」は選択内容に応じて表示が変わる。

---

# 4. 初期状態

新規登録画面を開いた直後に表示するものは最小限にする。

```text
以前の項目から選ぶ >

タイトル

予定の種類
日時が決まっている >
```

予定の種類は、通常のカレンダー利用が最も多いことを想定し、初期値を `日時が決まっている` にしてもよい。

ただし初期値を自動選択した場合でも、ユーザーが「期間中にやりたい」へ簡単に切り替えられること。

Calendar / Daily から特定日を指定して追加した場合は、その日を初期日として引き継ぐ。

---

# 5. 予定の種類

項目名:

`予定の種類`

選択肢:

- 日時が決まっている
- 期間中にやりたい

BottomSheet で選択する。

## 5.1 日時が決まっている

普通のカレンダー予定。

例:

- 9/20 15:00 歯医者
- 9/18〜9/20 東京旅行
- 9/21 終日 誕生日

## 5.2 期間中にやりたい

実施する日付・時刻は決まっていないが、ある期間内に行いたい予定。

例:

- 今週中にクリーニングを取りに行く
- 今月中に美容院へ行く
- 9/8〜9/12の間に役所へ行く

Todoの完了管理を中心にせず、LifeHub上では予定の一種として扱う。

---

# 6. 「日時が決まっている」を選んだ場合

予定の種類の下に日時設定を表示する。

基本構成:

```text
日付
9月20日 >

終日
OFF

時間
15:00 〜 16:00

繰り返し
なし >
```

## 6.1 日付

最初は単日予定として見せる。

通常表示:

```text
日付
9月20日 >
```

日付設定 BottomSheet 内で必要な場合のみ終了日を設定できるようにする。

例:

```text
開始日  9月18日
終了日  9月20日
```

複数日予定を登録しないユーザーに、常時「開始日 / 終了日」の2入力を見せない。

単日の場合:

`startDate = endDate`

とする。

## 6.2 終日

日付決定後に表示する。

```text
終日
OFF
```

### ON

時間入力を完全に非表示にする。

```text
日付
9月20日 >

終日
ON

繰り返し
なし >
```

### OFF

時間入力を表示する。

```text
時間
15:00 〜 16:00
```

開始時刻と終了時刻は同じ行または日時用 BottomSheet で設定する。

終了時刻の適切な初期値は実装時に既存UIとの整合を見て決める。

---

# 7. 「期間中にやりたい」を選んだ場合

時間・終日は表示しない。

基本構成:

```text
実施時期
今週中 >

繰り返し
なし >
```

項目名は `実施時期` とする。

選択肢:

- 今週中
- 今月中
- 日付範囲を指定

## 7.1 今週中

現在の週の中でいつ実施してもよい。

```text
実施時期
今週中 >

繰り返し
なし >
```

繰り返しを設定する場合、許可するのは:

- なし
- 毎週

### 毎週 + 今週中

毎週ごとに、その週のどこかで実施する予定が1件発生する。

例:

`毎週、週のどこかで掃除用品を補充する`

次週になると新しい「今週中」が発生する。

## 7.2 今月中

現在の月の中でいつ実施してもよい。

繰り返しを設定する場合、許可するのは:

- なし
- 毎月

### 毎月 + 今月中

毎月ごとに、その月のどこかで実施する予定が1件発生する。

例:

`毎月、月のどこかで美容院へ行く`

## 7.3 日付範囲を指定

任意の開始日〜終了日を設定する。

例:

```text
開始日  9月8日
終了日  9月12日
```

初期版では `日付範囲を指定` と繰り返しを組み合わせない。

そのため、この選択時は「繰り返し」自体を非表示にする。

---

# 8. 繰り返し

繰り返しは、予定の日時・実施時期が決まった後に設定する。

ユーザーの思考順として、

`いつ？ → これを繰り返す？`

となるため、繰り返しを日時より上に置かない。

通常時は1行だけ表示する。

```text
繰り返し
なし >
```

押したときだけ BottomSheet で詳細を設定する。

## 8.1 scheduled Event

日時が決まっている予定では、少なくとも以下を想定する。

- なし
- 毎日
- 毎週
- 毎月
- カスタム

詳細は RecurrenceRule 仕様に従う。

例:

- 毎週火曜日 10:00
- 毎月25日
- 2週間ごとの月曜日

## 8.2 period Event

期間中にやりたい予定では、実施時期によって選択肢を制限する。

| 実施時期 | 許可する繰り返し |
|---|---|
| 今週中 | なし / 毎週 |
| 今月中 | なし / 毎月 |
| 日付範囲を指定 | なしのみ。繰り返しUIを非表示 |

無効な選択肢を表示してエラーにするのではなく、最初から選択肢として出さない。

---

# 9. 通知

繰り返しの後に表示する。

通常表示は1行だけ。

```text
通知
なし >
```

またはデフォルトテンプレートが設定されている場合:

```text
通知
1日前・30分前 >
```

押すと BottomSheet で設定する。

選択候補:

- 通知なし
- 通知テンプレート
- カスタム

カスタムでは複数通知を追加できる。

例:

- 1週間前
- 1日前
- 1時間前
- 30分前

### 期間中にやりたい場合

period Event の通知ルールは scheduled Event と意味が異なるため、詳細仕様は通知設計で確定する。

未確定のルールを Codex が独自判断で実装しないこと。

---

# 10. 場所

予定の主要入力ではないため、最後の方に置く。

未入力時:

```text
場所
追加 >
```

入力済み:

```text
場所
○○歯科 >
```

押したときだけ入力UIを開く。

period Eventでも必要なら利用可能とする。

---

# 11. メモ

場所と同様、未入力時は大きな textarea を常時表示しない。

```text
メモ
追加 >
```

入力済みの場合は1行程度の要約を表示してよい。

長文編集は BottomSheet またはフォーム内展開で行う。

Event.memo と DailyNote は別物。

---

# 12. 「以前の項目から選ぶ」

HouseToDo のUXを強く参考にする。

フォーム最上部に:

```text
以前の項目から選ぶ >
```

を配置する。

選択すると、再利用可能な値をフォームへ反映する。

候補:

- title
- category
- timingType
- allDay
- 時間帯
- recurrence
- notifications
- place
- memo

ただし、Calendar / Daily から引き継いだ登録対象日は優先する。

過去予定の日付をそのままコピーしてしまわない。

例:

9/20のCalendarから「歯医者」を再利用した場合:

- タイトル: 歯医者
- 場所: ○○歯科
- 時間: 15:00
- 通知: 1日前
- 日付: 9/20

のように新しいcontextへ合わせる。

---

# 13. 編集画面

新規登録と同じフォーム構造を使用する。

既存値を各行のsummaryへ復元する。

繰り返し予定を編集するときは、編集対象範囲を先に選ぶ。

- この予定のみ
- この予定以降
- すべての予定

詳細なデータ処理は `RECURRENCE_AND_OCCURRENCE.md` に従う。

UIとしては編集画面そのものを3種類作らず、対象範囲を決めた後は同じフォームを利用する。

---

# 14. 削除

繰り返しなし:

- この予定を削除

繰り返しあり:

- この予定のみ削除
- この予定以降を削除
- すべての予定を削除

削除確認は破壊的操作として明確にするが、不要に何段階も確認を増やさない。

---

# 15. Calendar / Daily からの初期値

HouseToDo の `returnTo` と Calendar quick add の考え方を採用する。

## Calendarの日付から追加

その日を初期日として使用する。

例:

9/20を開いて追加

→ scheduled Eventの初期日 = 9/20

→ period Eventの `今週中 / 今月中` も9/20を含む週・月を基準にする

## Dailyから追加

表示中の日付を同様に引き継ぐ。

## 登録後

元の画面・選択日へ戻る。

---

```text
日付
↓

├─ ON  → 時間を表示しない

↓

↓

↓

↓

↓

```

## 16.2 period

```text

```

# 17. UIスタイル

HouseToDoの登録フォームを最重要参考元とする。

特に以下を維持する。

- smartphone-first
- 390×844 を主要確認サイズとする
- 1行の設定row + summary
- rowタップで BottomSheet
- 広すぎる空白を作らない
- 不要な説明文を常設しない
- safe area対応
- 入力完了後にフォーム全体が縦長になりすぎない
- titleなど必須入力と、場所・メモなど任意入力の視覚的重みを分ける

新しいUIパターンをむやみに追加せず、HouseToDoの既存design languageを優先する。

---

# 18. Codex実装時の禁止事項

設計段階では以下を勝手に補完しない。

- period Eventの通知タイミング
- `日付範囲を指定 + recurrence`
- 無効なrecurrence組み合わせをエラー表示で解決すること
- 全フィールドを最初から表示すること
- stepper / wizard形式への変更
- HouseToDoのTaskFormモデルをそのままコピーすること

未確定事項は仕様書に従って未確定のまま扱い、実装着手前に設計を確認する。
